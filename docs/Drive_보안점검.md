# Google Drive 연동 보안 점검
점검일: 2026-10-08. 대상: 관리자 Apps Script 수신 웹 앱, 사용자 전송 코드, 배포/업데이트, 비식별 검증. 최초 점검의 Drive 배포는 아래 GitHub 전환 결과로 대체됐습니다.
판정: 기본 인증/분리/업데이트 검증은 동작하나, 보완 코드의 실제 웹 앱 반영과 운영 위험 처리가 필요합니다. 보안 인증이나 침해 흔적에 대한 포렌식 결과는 아닙니다.

## 실제 서비스에서 확인한 내용
- 기존 배포 웹 앱: 잘못된 설치 키로 pull → AUTH_FAILED, 임의 getPackages → INVALID_REQUEST, 다른 설치ID에 기존 검증용 키로 pull → AUTH_FAILED.
- 위 응답에 전송 키나 packages가 노출되지 않았습니다. 소유 계정 로그인 없이 검증용 설치만 사용했고 사용자 기록을 가져오지 않았습니다.
- 공개 MC 목록에는 MyCivil3DMcp-release만 나타났습니다. 수신 데이터는 별도 MyCivil3DMcp-data를 사용합니다.
- 공개 목록 확인은 모든 파일의 ACL 확인을 대신하지 않습니다. 현재 실제 수집폴더/파일의 개별 사용자 공유, 공개 MC 편집자 목록, 관리자 계정의 2단계 인증 설정은 확인하지 못했습니다.
- 설치 EXE 0.1.4: Get-AuthenticodeSignature 결과 NotSigned입니다. 기존 RSA 별도 서명과 Windows 게시자 서명은 다른 기능입니다.

Drive의 PRIVATE 및 getSharingAccess 범위는 [Google Drive 서비스 문서](https://developers.google.com/apps-script/reference/drive/)에 명시돼 있습니다.
소유자 권한으로 실행되는 웹 앱은 [Google 웹 앱 안내](https://developers.google.com/apps-script/guides/web)를 따릅니다.
Google 자체 실행 한도는 [Apps Script 쿼터](https://developers.google.com/apps-script/guides/services/quotas)에도 적용됩니다. 코드 한도로 모든 과부하를 막을 수는 없습니다.

## 보완 적용 방법
1. Apps Script 편집기에서 저장소 scripts/google-ingest/Code.gs와 Validation.gs의 최신 내용을 각각 다시 붙여 넣고 저장합니다. appsscript.json은 그대로 유지합니다.
2. 함수 선택 목록에서 auditIntakePermissions를 선택하고 실행합니다.
   - 결과 safe: true, unsafe: [], truncated: false이면 검사한 범위의 공개/개별 공유가 없습니다.
   - unsafe가 있으면 표시된 폴더/파일의 공유를 Google Drive에서 관리자 소유 계정 외에 제거하고 다시 검사합니다.
   - truncated: true는 미완료이며 안전 판정이 아닙니다. 한 번에 500개/약 90초까지만 검사합니다.
   - 이 검사는 DriveApp이 노출하는 사용자 권한을 대상으로 합니다. 조직 관리자·그룹·계정 자체의 보안 감사까지 수행하지는 않습니다.
3. 배포 → 배포 관리 → 기존 웹 앱의 수정(연필) → 버전: 새 버전 → 배포.
   기존 배포를 수정해야 /exec URL이 유지됩니다. 새 프로젝트/새 폴더를 만들거나 setupIntake를 다시 실행할 필요는 없습니다.
4. 반영 뒤 실제 웹 앱 준비 상태 및 격리된 검증용 전송을 다시 확인해야 합니다.
5. 보완 코드가 실제 웹 앱에 반영되기 전에는 기존 서비스의 보호 수준이 바뀌지 않습니다.
   로컬 dist의 0.1.4 EXE도 이번 점검 후 재빌드한 파일이 아닙니다. 다음 패키지 생성 시 변경된 관리자 검증기가 포함됩니다.

## 재배포 후 확인

사용자의 기존 웹 앱 재배포 완료 안내 후 동일한 /exec 주소에서 실제 통신을 다시 확인했습니다.

- 준비 상태 정상, 검증용 설치의 기록 전송 ACK와 비공개 Drive 파일 해시 일치, 같은 묶음 재전송 중복 방지 통과.
- 잘못된 키와 다른 설치ID 요청은 AUTH_FAILED, 임의 조회는 INVALID_REQUEST로 거절.
- 배열 형태 토큰은 INVALID_REQUEST, 합성 API 키 패턴을 포함한 검증용 묶음은 INVALID_DATA로 거절. 보완된 입력 검증과 수신 키 필터가 실제 서비스에 적용된 것을 확인했습니다. 실제 비밀 키를 전송하지 않았습니다.
- 공개 MC 목록에는 MyCivil3DMcp-release만 나타났습니다.
- 권한 변경이나 하루 한도 소진은 실제 서비스에서 재현하지 않았습니다. 전체 ACL 감사의 실행 결과는 관리자 편집기에서 확인해야 합니다.
- 이 재배포는 Apps Script 웹 앱에 대한 반영입니다. 기존 dist 0.1.4 EXE는 변경하지 않았으며 Windows 게시자 서명과 공개 EXE 다운로드 차단은 별도 상태입니다.
- 결과: .package-work/security-audit/redeployed-results.json. 전송 키는 포함하지 않습니다.


## GitHub 배포 전환 확인

0.1.5부터 설치와 자동 업데이트는 공개 배포 전용 `wocl123/civil3d-mcp-releases`를 사용합니다. 비공개 소스 저장소의 공개 전환이나 소스 푸시는 하지 않았습니다. Release에는 EXE, RSA 서명, SHA-256, 서명된 최신 버전 정보만 게시합니다. 배포 시 Release 변경 방지를 활성화하고 초안의 파일 업로드를 마친 뒤 공개했습니다.

- 실제 로그인 없는 GitHub 최신 버전 조회, 메타데이터 RSA 검증과 EXE 다운로드의 원본 일치를 확인했습니다.
- 설치 EXE의 GitHub 채널·기존 수신 URL·관리자 메일을 검사하고 임시 경로에서 최초 설치·업데이트·데이터 유지·변조 거부를 검증했습니다.
- 다른 저장소/태그, 외부 다운로드 주소, 위조 서명, 초과 크기, 미완성 Release와 요청 제한 응답은 업데이트를 거부합니다. Google/GitHub 계정 토큰을 사용자 설치본에 넣지 않습니다.
- Apps Script 수신과 비공개 데이터 폴더는 유지합니다. 배포 위치 변경 자체가 수신 API의 공개 등록, 스팸·할당량 또는 데이터 비식별 처리의 한계를 해결하지는 않습니다.
- Windows Authenticode 서명 부재와 관리자 서명 비밀 키 접근 권한의 검토 필요성은 유지됩니다. 기존 설치본은 GitHub 채널을 받기 위해 새 EXE로 한 번 설치해야 합니다.


## 기존 저장소로 통합

사용자의 공개 전환 및 별도 저장소 삭제 요청에 따라 0.1.6부터 설치와 업데이트 채널을 `wocl123/civil3d-mcp`로 변경했습니다. 기존 소스 저장소를 공개로 전환했으며, 새 EXE의 team.json에도 동일한 채널을 넣었습니다. Google 데이터 수신 URL과 비공개 수집폴더는 유지합니다. 기존 원격 ZIP 배포 워크플로는 비활성화해 관리자 BAT의 서명된 EXE 게시와 충돌하지 않도록 했습니다. 소스 커밋·푸시는 하지 않았습니다. 0.1.5 설치본의 채널은 옛 저장소를 가리키므로 0.1.6 EXE로 한 번 재설치해야 합니다.
