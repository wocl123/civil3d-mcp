# 데이터 관리 설계

2026-10-06(2026-10-08 구글 드라이브로 변경). 이 PC의 데이터와 관리자에게 모으는 데이터를 어떻게 저장하고, 가리고, 보내고, 지우는지 정한다.
코드를 바꿀 때는 이 문서도 같이 고친다.

## 1. 원칙

1. **한 곳에 둔다.** 사용자 데이터는 `%LOCALAPPDATA%\MyCivil3DMcp\data` 한 곳에만 둔다(`MY_CIVIL3D_DATA_DIR`로 바꿀 수 있음).
   설치 폴더에는 두지 않는다. 예전처럼 "설치 폴더에 못 쓰면 다른 곳"으로 갈라지는 일을 없앤다.
2. **내용은 보내되, 누구의 무엇인지는 가린다.** (2026-10-07 변경: 결과를 정제해 이상한 답을 줄이려면 내용이 필요하다.)
   질문·답, 도구 입력, 도면 변경 설명은 보낸다. 보내기 전에 도면 파일 이름, 경로, 메일, Windows 사용자·PC 이름, 키 형태 문자열을
   `<이름>`, `<파일>`, `<경로>`, `<메일>`, `<키>`로 바꾼다. 도면 파일 자체는 보내지 않는다.
   팔레트는 처음 한 번 이 사실을 알린다. 모인 내용은 관리자(검토자)만 본다(`/검토 사례`).
3. **허용 목록으로 만든다.** 보내는 기록은 정해진 필드만 골라 새로 만든다. 원래 기록에서 지우는 방식(차단 목록)이 아니다.
   관리자 PC도 가져올 때 같은 허용 목록으로 다시 거른다(모르는 필드는 버린다).
4. **마지막 검사에서 걸리면 보내지 않는다.** 묶음(패키지)을 보내기 직전에 경로·메일·도면 이름 같은 흔적을 한 번 더 찾는다.
   걸리면 `outbox/blocked`에 사유와 함께 남기고 보내지 않는다.
5. **사람이 승인해야 모두에게 간다.** 다른 사용자 데이터로 만든 제안(통계)과 지식 후보는 검토자가 승인해야 중앙 지식이 된다.
   승인 전 내용은 어떤 AI 프롬프트에도 들어가지 않는다.
6. **사용자는 할 일이 거의 없다.** 처음에 보내기 폴더를 관리자와 한 번 공유하면, 기록, 비식별 처리, 전송, 중앙 지식 받기, 정리는 모두 자동이다.
   관리자 PC가 꺼져 있어도 사용자 드라이브에 쌓여 있다가 관리자가 켜면 가져간다.
7. **기한이 있다.** 모든 데이터에 보관 기한이 있다(§7).

## 3. 보내는 기록(허용 목록, schema 1)

시각은 시간 단위로 줄인다(`2026-10-06T13`). 오류는 원문 대신 실패 안내의 종류(`errorKind`)만 보낸다.
모든 기록에 그 기록을 남길 때의 프로그램 버전(`appVersion`, 예: `0.1.0`, 개발 폴더면 `dev`)을 붙인다. 업데이트 전후 기록이 한 묶음에 섞여도 구분되고, 관리자 보고서(`/검토 보고`)에 버전별 설치 수·질문 수·실패율이 나온다.

| type | 필드 | 쓰임 |
|---|---|---|
| `turn` | id, conversation, **question, answer**(가림), kind, provider, model, ms, cached, tools[], usage, counts{recorded, candidates, fixes, applied}, errorKind | 내용 분석, 느린 질문, 실패, 토큰 |
| `tool` | turnId, tool, **input**(가림), ms, ok, outputChars, images, errorKind | 도구별 실패율·속도, 어떤 값으로 불렀나 |
| `change` | turnId, state(applied/failed/**undone**), **title, labels**(가림), source(create/fix), check, changes[{kind, property, before, after}], curves, errorKind | 수정안이 적용되는지, **적용했다가 되돌렸는지** |
| `modification` | source, objectKind, property, aiValue, userValue, outcome, ageHours, conditions{designSpeed, roadClass, region, criteria} | **사람이 AI 결과를 고쳤는지(학습 신호)** |
| `feedback` | turnId, rating(bad), reason(가림) | **사용자가 답이 이상하다고 표시(팔레트 👎)** |

`check`는 코드가 기준표에서 만든 문구다(예: `제19조 최소 평면곡선 반지름`). 측점, 핸들, 선형 이름, 수정안 제목은 보내지 않는다.

지식 후보는 따로 보낸다. 보내는 필드는 localId, title, content, parameter, provider, 날짜다. 근거(사용자 말 인용)는 보내지 않는다.
content에 도면 이름 같은 가릴 낱말이 있으면 `<이름>`으로 바꾼다. 경로는 `<경로>`로 바꾼다.

### 문제 사례 (결과 정제의 출발점)

관리자 PC는 모은 기록에서 아래 신호가 있는 질문을 내용과 함께 모은다(`/검토 사례`, 관리자 전용).
같은 질문의 도구 호출·변경·평가는 `turnId`로 묶는다.

| 신호 | 뜻 |
|---|---|
| 👎 (feedback) | 사용자가 이상하다고 표시. 이유가 있으면 함께 |
| 되돌림 (change undone) | 적용했다가 되돌림. 결과가 틀렸을 가능성이 높다 |
| 변경 실패, 질문 실패 | 도면 변경이나 질문 처리 자체가 실패 |

**한 바퀴(반복):**

```text
① 사용자 데이터가 드라이브를 거쳐 관리자 PC로 (👎·되돌림·실패 = 문제 사례, 내용 포함·가림)
② 검토자 확인: /검토 사례 → 처리(분류·메모) 또는 버림(내용 삭제)
③ AI로 수정: 팔레트 /검토 사례 내보내기 → data\admin\수정요청-<날짜>.md
             → 저장소에서 Claude Code /fix-cases <그 파일> (원인·수정·회귀 시험·전체 시험)
④ 재배포: 새버전내기.bat → GitHub 빌드 → /중앙 배포 <버전> → 각 PC 자동 업데이트
⑤ 자료 삭제: /검토 사례 <번호> 완료 <버전> (그 사례 내용 삭제) → /검토 정리 (남은 질문 내용 삭제)
```
관리자 보관함에는 숫자 통계와 처리 기록(분류·메모·고친 버전)만 남는다. 보관 기한은 두지 않는다.

분류는 관리자 PC의 `data\admin\cases.json`에 남는다.

| 명령 (검토자 팔레트) | 하는 일 |
|---|---|
| `/검토 사례` | 아직 분류하지 않은 사례(기간 제한 없음) |
| `/검토 사례 <번호>` | 질문·답·사용자 의견·도면 변경·도구 |
| `/검토 사례 <번호> 처리 <지식\|코드\|AI\|기타> [메모]` | 처리할 것으로 분류 → 할 일 목록 |
| `/검토 사례 할일` · `/검토 사례 완료` | 할 일 목록 · 처리 끝난 목록 |
| `/검토 사례 <번호> 완료 [버전] [메모]` | 처리 끝(몇 버전에서 고쳤는지). 그 사례 내용 삭제 |
| `/검토 정리` | 한 바퀴 정리: 분류 전·할 일 사례만 남기고 나머지 질문의 내용 삭제 |
| `/검토 사례 <번호> 버림 [메모]` | 버림: 관리자 보관함에서 그 질문의 내용(질문·답·도구 입력·변경 설명·의견)을 지움. 숫자 통계만 남음 |
| `/검토 사례 <번호> 취소` | 분류 취소(버린 것은 되돌릴 수 없음) |
| `/검토 사례 내보내기 [new\|todo\|done\|all]` | 사례(기본: 할 일)를 AI 수정 요청서(.md)로 내보내기 |
| (개발 PC, Claude Code) `/fix-cases 수정요청.md` | 원인 찾기 → 수정 → 회귀 시험 → 전체 시험 → 결과 표 |

원인에 따라: 지식이 부족하면 지식으로 승인, 코드 문제면 고친 뒤 그 사례를 회귀 시험에 넣는다(다음 버전에서 다시 틀리지 않게).

### 마지막 검사(패키지 전체 문자열)

- 드라이브 경로(`C:\`, `D:/`), UNC 경로(`\\server`), 메일 주소, `.dwg`/`.dxf` 파일 이름
- Windows 사용자 이름, PC 이름
- `terms.json`의 낱말(3자 이상)

하나라도 걸리면 그 패키지는 보내지 않는다. 관리자 PC도 가져올 때 같은 규칙으로 다시 검사하고, 걸리면 받지 않는다.

## 4. 사용자 수정 추적

AI가 도면을 바꾸면 그 값을 `tracking\`에 남긴다. 대상은 선형 생성과 수정안 적용이다.

| 대상 | 읽는 곳 | 찾는 기준 |
|---|---|---|
| 생성 선형의 곡선 반지름·완화곡선 길이 | alignment.section `elements` | 곡선 그룹 번호 |
| 수정안: 원곡선 반지름 | 위와 같음 | 수정안 대상의 곡선 번호 |
| 수정안: PVI 표고 | profile.section `pvis` | PVI 측점 |
| 수정안: 종단곡선 길이 | profile.section `curves` | PVI 측점 |

- **언제 확인하나:** 팔레트 질문이 시작될 때와 동기화 주기마다 확인한다. 열린 도면이 같고, 도면 revision이 지난 확인 때와 다를 때만 읽는다.
- **결과 종류:**
  - `modified`: 값이 바뀜. 바뀔 때마다 기록한다.
  - `deleted`: 객체가 없어짐.
  - `restructured`: 곡선 개수가 달라져 비교할 수 없음.
  - `kept`: 14일 동안 그대로.
- **기록이 끝나는 때:** `deleted`, `restructured`, `kept`가 되면 추적을 끝낸다.
- **알 수 없는 것:** 사용자가 도면을 저장하지 않고 닫으면 알 수 없다. 이 기록은 "그 사이에 고친 적이 있다"는 뜻이지, "최종 도면이 그렇다"는 뜻이 아니다.

## 5. 설정값(승인된 관행 → 코드)

관행 중에는 숫자로 바꿔 코드가 직접 쓸 수 있는 것이 있다. 이런 것은 정해진 설정값으로 둔다.

| 키 | 뜻 | 정하지 않았을 때 | 허용 값 |
|---|---|---|---|
| `alignment.radiusStep` | 평면곡선 반지름 올림 단위(m) | 선형 계획 5, 수정안 1 | 1, 5, 10, 50, 100 |
| `alignment.spiralStep` | 완화곡선 길이 올림 단위(m) | 1 | 1, 5, 10 |
| `profile.curveLengthStep` | 종단곡선 길이 올림 단위(m) | 1 | 1, 5, 10, 20 |

- **우선순위:** 이 PC에서 승인한 값 > 중앙 값 > 기본값.
- **화면 표시:** 기본값이 아닌 값을 쓰면 계획·수정안의 notes에 어디서 온 값인지 적는다.
- **AI가 제안하는 경우:** AI가 일반 관행을 기록할 때, 관행이 위 키에 해당하면 `parameter: {key, value}`를 붙인다. 허용 값이 아니면 버린다.
- **답변 캐시:** 설정값이 바뀌면 답변 재사용 키도 바뀐다.

## 6. 구글 드라이브로 모으기 (서버 없음)

2026-10-08부터 중앙 서버 대신 구글 드라이브(Google Drive for Desktop) 공유로 모은다. 서버를 켜 둘 PC, 고정 IP, 방화벽, 인증서가 필요 없다.
코드: `server/src/drive/`(폴더 찾기, 사용자 쪽), `server/src/admin/`(관리자 쪽: 보관함, 검토, 검사, 배포).

```text
사용자 PC의 "내 드라이브"
  MyCivil3DMcp-<설치 ID>/        보내기 폴더(서비스가 만든다)
    member.json                  어느 설치의 폴더인지
    packages/<id>.json           비식별 묶음        ← 사용자 PC가 넣음
    candidates/<id>.json         지식 후보(비식별)   ← 사용자 PC가 넣음
    admin/received.json          관리자가 가져간 id  ← 관리자 PC가 씀 → 사용자 PC가 그 파일들을 지움
    admin/official.json          승인 지식·설정값    ← 관리자 PC가 씀 → 사용자 PC가 적용
    admin/release.json + zip     배포 버전           ← 관리자 PC가 씀 → 사용자 PC가 자동 업데이트
```

- **가입 = 공유:** 사용자가 보내기 폴더를 관리자 메일과 **편집자**로 공유한다(팔레트 `/중앙`이 방법을 알려 준다). 관리자에게 Gmail 알림이 간다.
- **승인 = 바로가기 추가:** 관리자가 공유 문서함에서 그 폴더를 "내 드라이브에 바로가기 추가"하면 관리자 PC에도 동기화되고, 관리자 서비스가 찾아 가져온다.
  관리자 PC 팔레트 아래 줄에 "새 사용자 n"이 1분 안에 보인다(`/중앙 사용자`). 모르는 폴더는 `/중앙 사용자 <번호> 차단`.
- **관리자 보관함:** 관리자 PC의 `data\admin\`(기록 `records\<월>.jsonl`, 후보, 승인 지식과 이력, 결정, 사례 분류, 사용자 목록, 받아 둔 배포본).
- **검사:** 관리자 PC가 가져올 때 예전 서버와 같은 허용 목록으로 다시 거르고(`admin/validate.ts`), 경로·파일 이름·메일이 남은 묶음·후보는 받지 않는다.
  받지 않은 파일도 `received.json`에 적어 사용자 드라이브에서 지운다.
- **위조:** 폴더마다 설치 ID가 있다. 이미 다른 폴더가 쓰는 설치 ID를 주장하는 폴더는 가져오지 않는다. 묶음 id는 그 설치 ID로 시작해야 한다.
  사용자는 자기 폴더의 `admin/`을 고칠 수 있지만 자기 PC에만 영향이 있고, 배포 zip은 설치 프로그램이 서명을 확인한다.
- **이름:** 폴더 이름에는 익명 설치 ID만 있다. 누구의 폴더인지는 관리자가 구글 드라이브에서 소유자로 본다. 작업 기록의 이름은 지금처럼 가린다.
- **팀 정보:** GitHub 릴리스 zip에 `team.json`(관리자 메일, 저장소 Variables `ADMIN_EMAIL`)이 들어 있다. 설치하면 `data\team.json`으로 복사되고,
  서비스는 따로 설정하지 않아도 사용자 PC로 동작한다. 없으면 `/중앙 신청 <관리자 메일>`.
- **드라이브 위치:** `G:\내 드라이브`처럼 드라이브 문자 아래(스트리밍)나 사용자 폴더 아래(미러링)를 찾는다. 다르면 `/중앙 드라이브 <경로>`.
- **배포:** 관리자가 `/중앙 배포 <버전>` → 이 PC의 `gh`(GitHub CLI) 로그인으로 Release의 zip·.sha256·.sig를 받아 서명을 확인하고 → 각 사용자 폴더 `admin/`에 넣는다.

### 통계 자동 제안("다른 사용자에게서 배우기")

- **후보 묶기:** 띄어쓰기와 문장부호를 뺀 내용이 같은 후보를 한 묶음으로 본다. 지지 = 서로 다른 설치 수다.
- **설정값 제안:** `modification`(modified) 중 같은 속성에서 아래를 모두 만족하면 `alignment.radiusStep = s`를 제안한다.
  - 사람이 고친 값이 s의 배수다.
  - AI 값은 s의 배수가 아니었다.
  - 이런 경우가 그 속성 수정의 80% 이상이다.
  - 경우가 5건 이상이다.
  - 서로 다른 설치 2곳 이상에서 나왔다.
  - 기준(`minInstalls`, `minCases`)은 관리자 PC의 `data\admin\config.json`에 있다.
- **유지율 보고:** AI가 만든 값이 그대로 남았는지(kept), 고쳐졌는지(modified), 지워졌는지(deleted)를 보고한다. 이 결과는 규칙 개선의 근거다.

제안은 검토자의 `/검토` 목록에 지지 수와 함께 나온다. 승인하면 중앙 지식 버전이 1 오르고, 관리자 PC가 다음 동기화(10분 이내)에 각 사용자 폴더에 넣으면 그 PC가 받아 적용한다.

## 8. 동기화 주기(로컬 서비스)

동기화는 서비스 시작 5초 뒤, 10분마다, 질문이 끝나고 10초 뒤에 돈다. 한 번에 하나만 돈다. 순서는 아래와 같다.

1. 수정 추적 확인(열린 도면)
2. 새 로그를 읽어 비식별 패키지를 만들고, 마지막 검사를 거쳐 `outbox`에 넣음(드라이브와 무관)
3. 사용자 PC: 관리자가 가져간 파일 지우기 → 패키지·후보를 보내기 폴더로 → 승인 지식 받기
   관리자 PC: 이 PC 기록 가져오기 → 사용자 폴더마다 가져오기(검사) → `received.json`·승인 지식·배포본 넣기 → 이 PC에도 승인 지식 적용

1분마다 관리자 PC는 새 사용자 폴더 수를 센다(팔레트 아래 줄).
