# my-civil3d-mcp 작업 계획

작성: 2026-10-07 · 보완: 2026-10-07 코드 대조 및 배포 검토

목표는 **다른 사람 PC에서 개발 환경 없이 설치하고, 질문·도면 변경·되돌리기까지 사용할 수 있는 상태**다.
첫 배포 대상은 Windows x64와 Civil 3D 2025다. 2026은 별도 검증 후 지원한다.
설치·로그인에는 인터넷과 사용자의 AI 계정이 필요하다. 로그인은 사용자가 직접 진행한다.

이 문서는 실행 계획이다. 체크되지 않은 항목은 구현·검증 완료를 뜻하지 않는다.

---

## 현재 상태와 기본 설계

| 구성 | 현재 판단 | 남은 확인 |
|---|---|---|
| 플러그인 (`plugin/`) | 빌드와 도면 변경·작업 기록·팔레트 버튼 구현 존재 | 실제 Civil 3D의 삭제 종속 객체 복원, 배포 자동 로드 |
| 로컬 서비스·MCP (`server/`) | 설계·안정성·삭제 등 시나리오 검사 존재 | 배포본 실행, CLI 설치, 재연결 변경의 최종 검사 |
| 중앙 서버 (`central/`) | HTTP와 파일 저장 구현 존재 | 운영 전송 보호, 일관된 백업과 복원 |
| 배포 패키지 | 없음 | 런타임·파일 목록·설치·업데이트 전체 |

최근 삭제·되돌리기 검사와 안정성 17개 시나리오는 가짜 브리지 기반으로 통과했다.
전체 검사와 네이티브 Civil 3D 검증은 배포 대상으로 다시 실행한다. 줄 수·파일 수·검사 수는 고정 완료 기준으로 쓰지 않는다.

배포 구현은 다음을 기본안으로 진행한다.

- 공식 Windows x64 Node 배포본의 **node.exe와 npm 전체 구성**을 동봉한다. 정확한 버전과 SHA-256을 고정한다.
- 번들의 런타임은 읽기 전용으로 사용한다. npm 기반 AI CLI는 사용자 데이터 폴더의 별도 prefix에 설치한다.
- Claude SDK 한도 도우미(`claude-quota`)는 기본 패키지에서 제외한다. 상태줄 기록이 없으면 한도를 조회하지 못했다고 표시한다.
- 서비스·MCP는 동봉 Node를 사용한다. CLI 실행에도 해당 Node 경로가 전달되어야 한다.
- 기존 AI CLI를 사용하는 경우 지원 버전·실행 경로를 확인하고 진단 정보에 남긴다.

## 단계 1. 배포 패키지 (핵심, 예상 3~5일; 새 계정·CAD 검증 결과에 따라 조정)

### 1-1. 폴더와 버전 제한

```text
%APPDATA%\Autodesk\ApplicationPlugins\MyCivil3DMcp.bundle\
  PackageContents.xml
  Contents\
    plugin\                    플러그인 및 필요한 자체 의존성
    node\                      node.exe, npm.cmd, node_modules\npm\ 등 공식 런타임 구성
    server\                    package.json, package-lock.json, build\, 운영 node_modules\
                               skills\, knowledge-defaults\, setup\
    licenses\                  동봉 구성의 라이선스·고지
    version.json               제품·Node 버전, 빌드 시각, 소스 식별 정보, 지원 CAD
    manifest.json              배포 파일 목록과 SHA-256
```

- [ ] `RuntimeRequirements`: `OS="Win64"`, `Platform="Civil3D"`, `SeriesMin="R25.0"`, `SeriesMax="R25.0"`
- [ ] 시작 시 로드 조건과 플러그인 초기화를 검증한다. 번들 발견·DLL 로드·서비스 준비·팔레트 표시를 각각 확인한다.
- [ ] 플러그인 출력의 필요 파일을 목록으로 정한다. Autodesk 참조 DLL은 패키지에 포함하지 않는다.
- [ ] 런타임·라이선스·모든 파일 해시를 실제 패키지에서 검사한다.

사용자 데이터는 `%LOCALAPPDATA%\MyCivil3DMcp\` 아래에 둔다.
기존 데이터는 `data\`, npm 기반 CLI는 예를 들어 `cli\<provider>\`에 설치한다.
업데이트는 사용자 데이터·AI 로그인 정보를 덮어쓰지 않는다.

2025 설정 근거: [Autodesk Civil 3D .NET Core 안내](https://help.autodesk.com/cloudhelp/2025/ENU/Civil3D-DevGuide/files/GUID-B50CC834-E202-48FE-9C64-526EF9828535.htm).

### 1-2. 실행 경로·CLI 설치·한도 조회

- [ ] `NodeService.cs`의 서비스 위치: 개발 환경 변수 → 번들 → 기존 개발 폴더 순서
- [ ] Node 위치: 번들 → 호환 버전의 PATH Node → 설치 오류 안내 순서
- [ ] `paletteWorkspace.ts`의 `process.execPath` 사용을 유지하고, 실제 MCP 자식 프로세스 경로를 검사한다.
- [ ] `cliSetup.ts`, `setup-ai-cli.ps1`, `cliLocator.ts`, CLI 실행 환경을 함께 수정한다.
  - 동봉 Node와 npm의 절대 경로를 설치 창에 전달한다.
  - 설치 스크립트의 PATH 재구성 과정에서도 동봉 런타임 경로를 보존한다.
  - npm 기반 CLI는 사용자 prefix에 설치하고 설치 후 검색·로그인·실행에 같은 경로를 쓴다.
  - CLI 실행 중 `.cmd`가 Node를 찾을 수 있도록 동봉 런타임을 실행 환경에 포함한다.
  - 설치 버전·경로를 기록하고 CLI 설치 실패와 로그인 실패를 구분한다.
- [ ] CLI별 지원 버전과 옵션 호환성 검사를 정한다. 배포 검증에 사용한 버전을 기록한다.
- [ ] 설치 폴더 쓰기를 제거한다. 임시 작업·설정·로그·CLI 설치는 사용자 폴더로 보낸다.
- [ ] 기본 패키지에서 Claude SDK 도우미를 사용하지 않도록 명시적으로 분기한다.
  - 없는 도우미를 실행한 뒤 실패하는 경로를 제거한다.
  - 상태줄 기록 방식의 생성·연결 방법을 검증한다. 기존 사용자 설정을 임의로 덮어쓰지 않는다.
  - 기록 시각·만료를 확인한다. 기록이 없거나 오래되면 한도 조회 불가로 표시한다.
  - 새 계정에서 기록이 생성되지 않으면 한도 표시 없이 질문이 가능한지 확인한다.

### 1-3. 재현 가능한 패키지 생성

- [ ] `scripts/package.ps1`에 다음 순서를 구현한다.
  1. 빌드 입력·도구 버전 확인, 플러그인 Release 빌드
  2. 서버 `npm ci`로 개발 의존성까지 설치
  3. 서버 빌드와 필수 자동 검사
  4. 별도 패키지 준비 폴더에 `build`, 설정·지식·스킬·설치 스크립트 복사
  5. 준비 폴더에 서버 package.json·lockfile을 복사하고 `npm ci --omit=dev` 실행
  6. 고정한 공식 Node 배포본의 해시 검증 후 런타임과 라이선스 복사
  7. PackageContents.xml·version.json·파일 manifest 생성 및 검사
  8. 준비된 패키지 경로에서 실행 검사 후 `dist\MyCivil3DMcp.bundle`과 zip 생성
- [ ] 어느 단계든 실패하면 배포 결과물을 성공으로 게시하지 않는다.
- [ ] 개발 데이터·연결 토큰·AI 계정 파일·로그·작업 폴더가 패키지에 들어가지 않는지 검사한다.
- [ ] 패키지 실제 크기를 측정한다. `claude-quota` 제외에 따른 축소율은 측정 후 기록한다.

### 1-4. 설치·삭제·업데이트와 실패 복구

- [ ] `install.ps1`: 사용자 번들 폴더에 설치하고 파일 목록·해시·지원 환경을 확인한다.
- [ ] zip 경로가 설치 준비 폴더 밖으로 나가지 않도록 검사한다.
- [ ] 이미 설치되어 있으면 업데이트 흐름으로 처리한다.
- [ ] 업데이트 순서:
  1. Civil 3D 종료와 이 설치본이 시작한 Node 서비스 종료 확인
  2. 새 버전을 준비 폴더에 풀고 manifest 검증
  3. 기존 번들을 백업하고 새 버전으로 교체
  4. 복사·교체 실패 시 기존 번들 복구
  5. Civil 3D 재실행 후 버전·자동 로드·서비스 준비 확인, 문제 시 이전 버전 복원 경로 제공
- [ ] 다른 프로그램의 Node 프로세스를 이름만으로 종료하지 않는다.
- [ ] `uninstall.ps1`: 번들만 제거한다. 사용자 데이터 삭제는 명시적 선택으로 처리한다.
- [ ] 팔레트 또는 `MYC3DCONNECTION`에 제품 버전·지원 CAD·Node 버전·실행 경로 표시

### 1-5. 배포본 검증

가짜 브리지 검사와 실제 Civil 3D 검사를 따로 기록한다.

| 환경·상황 | 완료 조건 |
|---|---|
| 새 PC 또는 새 Windows 계정 | 기존 Node·npm·CLI와 개발 저장소 없이 설치 성공 |
| 번들 자동 로드 | NETLOAD 없이 2025에서 플러그인·서비스·팔레트 준비 |
| AI별 첫 사용 | 설치 → 로그인 → 질문 성공, 실패 원인 구분 |
| 읽기 전용 설치 폴더 | 질문·설정·로그·CLI 설치·MCP 실행 성공 |
| 한글·공백 경로 | 번들·사용자 폴더 경로에서 실행 성공 |
| 실제 CAD 변경 | 수정·삭제·되돌리기·재적용 및 종속 객체 복원 성공 |
| 후속 편집·도면 전환 | 오래된 변경 카드가 다른 편집을 취소하지 않음 |
| Civil 3D 두 개 실행 | 질문·변경·복구가 각 도면 연결에만 전달됨 |
| 서비스 재시작 | 대화·수정안·작업 상태 복구, 변경 중복 실행 없음 |
| 업데이트 실패 | 이전 버전으로 복구, 사용자 데이터 유지 |
| 제거 | 제거 후 Civil 3D 정상 시작, 기본 선택에서 사용자 데이터 유지 |

2026은 로드 외에 질문·편집·삭제·복구까지 별도로 검증한다. 통과 전 지원 범위를 확대하지 않는다.

**완료 기준:** zip 하나와 설치 명령으로 새 사용자 환경에서 질문·도면 변경·복구까지 된다.
인터넷·계정 로그인·지원 Civil 3D 설치는 전제 조건으로 안내한다.

## 단계 2. 중앙 서버 운영 준비 (예상 1~2일, 운영 환경에 따라 조정)

- [ ] 사내망·외부 접근 범위와 운영 담당자를 정한다.
- [ ] 운영 전송은 HTTPS를 기본으로 설계한다. 개발 HTTP와 운영 설정을 구분한다.
  - 인증서는 운영 환경에 맞춰 리버스 프록시에서 관리한다.
- [ ] 가입키·검토자 키 교체 및 기존 설치 토큰의 폐기·재발급 절차를 문서화한다.
- [ ] 서버 시작·비정상 종료 후 재시작·로그 보존 절차를 정한다.
- [ ] 일관된 백업을 만든다. 초기 방식은 서비스 정지 → 데이터 백업 → 서비스 재시작으로 한다.
- [ ] 별도 폴더에 백업을 복원하고 설치 등록·승인 지식·버전·기록을 확인한다.
- [ ] 나중에 SQLite를 도입할 때는 저장소 인터페이스를 먼저 정리한다.
  - 현재 `server.ts`·`review.ts`가 Store 배열과 객체를 직접 접근한다.
  - 조회·등록·후보 수정·발행을 저장소 메서드로 모은 뒤 DB로 옮긴다.
  - `store.ts` 한 파일만 교체하면 된다는 완료 가정은 두지 않는다.

**완료 기준:** 다른 PC 설치본의 가입·기록 전송·승인 지식 배포와 백업 복원까지 확인했다.

| 위험 | 대응 |

| CLI 옵션 변경 | 검증 버전과 경로 기록, 호환성 검사, 설치·로그인·실행 오류 구분 |
| Claude 상태줄 기록 없음·만료 | 한도 조회 불가 표시, SDK 부재를 질문 실패로 연결하지 않음 |
| 설치 교체 중 실패 | 준비 폴더 검증·기존 버전 백업·복구 |
| 가짜 검사 통과 후 CAD 복구 실패 | 실제 Civil 3D의 종속 객체 복원 검사를 별도 배포 조건으로 둠 |
| 중앙 백업 불일치 | 서비스 정지 또는 일관된 스냅샷, 복원 검사 |
| 2026 비호환 | 2025 한정 배포, 별도 편집·복구 검증 후 지원 확대 |

## 진행 순서와 남은 환경 확인

```text
현재 변경 검증
  → 배포 경로·Node/npm·CLI 설치 설계
  → 패키지 생성 및 배포 폴더 실행 검사
  → 새 Windows 계정·실제 Civil 3D 변경/복구 검사
  → 설치·업데이트·실패 복구 완성
  → 중앙 운영 준비
  → 구조 정리
```

배포 구현은 위 기본안으로 진행할 수 있다. 다음 외부 조건은 해당 검증·운영 단계 전에 확인한다.

1. 깨끗한 PC 또는 새 Windows 계정과 Civil 3D 2025 검증 환경
2. 중앙 서버 접근 범위·도메인·인증서 관리 방식
3. AI별 설치·로그인 검증 계정과 Gemini 사용 가능 여부

## 배포 구현 진행 기록 (2026-10-07)

- 번들 우선 서비스·Node 경로, 최소 Node 버전 확인, 연결 진단의 제품/런타임 버전 표시 구현.
- 번들 자동 로드 후 첫 도면 Idle에서 팔레트를 여는 코드 구현(실제 CAD 확인은 대기).
- npm 동봉 및 사용자별 CLI prefix 설치·검색·실행 연결 구현. 시스템 PATH는 변경하지 않음.
- SDK 도우미 제외와 15분 이내 상태줄 기록 대체 경로 구현. 기존 Claude 설정은 변경하지 않음.
- package/install/uninstall 스크립트, 파일 manifest·Node 해시 검증, 설치 교체 실패 복구 구현.
- 독립 C# 경로 검사, 가짜 CLI의 한글·공백 prefix 설치 검사, 배포본 서비스·MCP 실행 검사 통과.
- 임시 폴더에서 설치·업데이트·이전 버전 보관·교체 실패 복구·파일 변조 거절·압축 경로 이탈 거절·제거·데이터 보존 검사 통과.
- 실제 새 Windows 계정의 CLI 설치·로그인, 읽기 전용 ACL, Civil 3D 자동 로드·삭제 종속 객체 복원은 미확인.
- 생성·설치 명령과 제한 사항은 [배포 설치 안내](배포_설치.md)에 정리함.
